# QuanX 全量规则同步项目设计

状态：用户于 2026-10-27 授权完成项目并上传到其 GitHub；按独立转换仓库实施。

## 需求与目的

创建一个独立 GitHub 项目，使用一个 GitHub Actions 工作流每天自动同步 MetaCubeX/meta-rules-dat 的全部分类，转换成 Quantumult X 可订阅的规则。用户已明确要求同步全部分类，并已于 2026-10-27 选择独立转换仓库。

本设计中的默认时间、技术选型、输出分支及兼容处理均为实现方建议，用户可修改。

## 方案比较

1. **独立转换仓库（推荐并用于本设计）**：读取上游 sing 分支已经生成的 JSON 规则，只维护 QuanX 转换、验证和发布逻辑。可以复用上游分类、避免重复构建规则库。
2. **Fork 上游并扩展构建**：修改上游完整构建流程，为 QuanX 增加产物；需要持续合并上游流程、安装整套构建依赖，维护范围明显更大。

用户已选择方案 1：独立转换仓库。方案 2 仅作为比较记录，不进入实施范围。

## 输入下载与一致性

先解析 sing 分支的完整提交 SHA，再下载该 SHA 的官方 GitHub 源码压缩包。在整个转换周期中只使用这一快照，不混用分支移动后的文件。

采用压缩包批量获取，避免对八万余分类逐文件发起请求。流式遍历成员，仅处理 JSON；不直接解包任意成员路径。校验路径、重复分类、JSON 结构、版本和字段。

全量发现包括已有三类顶层目录以及未来新增的 JSON 分类，保留其相对路径；新的目录不因名称未知而被忽略。遇到无法识别的 JSON 架构或字段，整次发布失败，等待维护者处理，而不是静默缺失。

下载超时、重试、压缩包读取失败、JSON 损坏、未知结构、非法规则内容等均使工作流失败，不发布部分结果。

## 转换与兼容边界

| 上游字段 | QuanX 输出 |
| --- | --- |
| domain | host |
| domain_suffix（无前导点） | host-suffix |
| domain_suffix（有前导点） | 保留仅匹配子域名的含义，使用经过验证的 host-wildcard；无法证实等价则整次失败 |
| domain_keyword | host-keyword |
| ip_cidr IPv4 | ip-cidr |
| ip_cidr IPv6 | ip6-cidr |
| domain_regex | 不尝试近似改写；逐条保留到兼容报告 |

每一条输出规则默认使用 `proxy` 策略；不自动根据分类名称猜测广告、直连或代理用途。订阅示例使用 force-policy 覆盖为用户已有策略组名称，遵循 QuanX 官方示例。

ASN 分类使用上游 JSON 中的 IP 网段生成规则，不改写为依赖客户端其他数据库版本的 ip-asn。

精确域名、后缀、关键词、IP 的合法值必须验证，拒绝逗号、换行等可能改变规则结构的输入。IP 使用标准库验证并规范化；确定顺序、去除相同规则，保留不同匹配类型的语义。

**全量分类同步不代表正则匹配可以无损转换。** 当前 66 个规则对象含 domain_regex；该值是对象数，并非正则条数。兼容报告须记录分类、原始表达式、跳过原因及条数。混合分类发布可支持的规则，同时标记 partial。全部内容不可转换或上游本身为空的分类，登记为 unsupported-only 或 empty，不发布空订阅文件，也不向订阅目录提供无效链接。每个源分类都必须在清单中可追溯。

对逻辑规则、反向匹配及未来未知条件，不能展开为可能扩大匹配范围的普通条目；初版不支持，检测到后使整次发布失败。不得用 URL 重写模拟域名路由正则。

## 产物与使用方式

源码默认在 main 分支；生成产物发布到独立 quanx 分支。订阅地址稳定为：

`https://raw.githubusercontent.com/<owner>/<repo>/quanx/rules/geo/geosite/google.list`

账号和仓库名由运行时的 GitHub 仓库上下文获取，不依赖手工替换脚本；本地运行可传入仓库名。

产物包括：

- rules/：对应上游目录的 .list 文件。
- index.md 和分组目录：提供全部可订阅分类的链接、规则数、完整或部分支持状态；ASN 分类索引按固定数量分页，避免单个巨大 Markdown 页面。
- reports/：兼容明细、各组分类清单及发布汇总，包含来源 SHA、源分类数、输出数、跳过规则数和每分类状态。
- README.md：中文使用说明、策略覆盖示例、更新方式、兼容边界和上游出处。

所有统计及报告均根据实际转换结果生成，分类总数必须与 manifest 各状态之和一致，所有订阅目录链接必须指向实际非空文件。

## 一个工作流的职责

文件建议为 `.github/workflows/update.yml`，一个工作流同时支持每日定时、手动触发，以及转换器或工作流更新后的验证和生成。Python 3.12+，优先标准库，避免依赖大型转换器或 Go 构建链。

建议每日北京时间 08:30 触发（UTC 00:30）。定时触发可能延迟；上游尚未完成当天构建时使用当时最新的完整快照，不声称一定获得当天产物。

工作流步骤：获取源码 → 运行离线测试 → 确定并下载上游快照 → 暂存目录全量转换 → 验证统计与文件 → 上传兼容报告至 Actions 摘要/产物 → 比较 quanx 分支 → 有变化才提交并推送。

发布使用仓库自带 GITHUB_TOKEN 和 contents: write，无需个人访问令牌。工作流并发发布串行执行；上游失败时现有订阅保持可用。首次运行可创建 quanx 分支，以后在当前远程头上正常提交，不强制推送，不修改上游仓库。

规则文件和兼容报告采用确定性输出，不写运行时间造成每日规则重写。来源 SHA 记录在汇总元数据中，便于追溯；只有元数据变化时允许小规模提交。连续处理同一个快照且实现未改变时，不产生新提交。大批删除、空结果等异常必须被检测，不能用上一次结果冒充本次成功。

部署说明须说明工作流需要在默认分支启用、仓库令牌写权限及分支保护可能阻止自动发布，以及 GitHub 对长期无活动的公共仓库定时任务的停用规则。不通过无意义提交或其他额外工作流规避该规则。

## 验证与验收

使用有实际语义价值的离线测试：五种基本字段、字符串/数组两种形式、IPv4/IPv6、前导点后缀、正则混合/仅正则/空分类、非法值、未知字段、版本不支持和逻辑条件；确保失败时不替换已有产物。

用已固定的真实上游快照执行一次全量转换，核对全部分类状态、转换总数及订阅文件；验证所有生成链接和规则行结构。记录运行时间、产物体积和不兼容条数，确认适合 GitHub Actions。

重复运行相同输入，比较所有文件内容应完全一致；模拟新增/删除分类，验证清单和产物更新；模拟下载失败，验证发布阶段不会执行。

检查工作流 YAML 与发布过程；若本会话尚未配置真实 GitHub 仓库，仅交付可上传项目和本地验证结果，不把 GitHub 定时任务描述为已经启用，不声称已在 QuanX 真机验证。

## 交付与留给实现方的选择

实现项目保存为 outputs/quanx-rules/，交付源码、工作流、测试、说明文档及压缩包；完整生成规则可以作为单独产物，避免用户手动上传八万多个文件。首次上传源码后通过手动运行工作流生成 quanx 分支。

内部模块拆分、索引分页条数、合理的运行时资源上限、退避重试参数由实现方决定并验证。上游授权及来源声明按实际许可证保留；实现阶段核对 LICENSE 的适用范围，不推断所有外部数据源拥有相同授权，不分发与转换无关的数据库或二进制产物。

用户已授权创建远程仓库、上传项目并启用每日更新；不涉及购买服务。
